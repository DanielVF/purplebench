# Compiler Tracking Implementation Plan

This document describes the implementation plan for a Rust + revm tool that
benchmarks changes to the Solidity compiler. The tool is intended for both long
running compiler tracking and fast compiler-development comparisons against a
baseline.

The workspace is currently empty, so this plan assumes a greenfield Rust CLI
project.

## 1. Product Goals

Primary metrics:

- Runtime bytecode size.
- Gas usage for sampled transactions.

Important constraints:

- Runtime bytecode size includes compiler metadata. Do not strip metadata for
  the primary metric.
- Creation bytecode is out of scope for the primary reports.
- Gas usage is expected to change between compiler versions. Gas deltas are
  benchmark data, not correctness failures by themselves.
- Transaction correctness is checked by comparing post-transaction storage slot
  behavior against the recording.
- Benchmark runs must be offline. All account data, storage slots, code, block
  data, transaction data, and expected post-transaction storage values must be
  stored in fixtures.
- Benchmark runs must be parallel.
- Outputs must be git-friendly CSV and static HTML built from that CSV.
- Reports must also produce concise textual diffs suitable for agents and
  terminal review.

Visual direction:

- Take color inspiration from https://www.soliditylang.org/.
- Use a warm, current, professional style.
- Prioritize dense data presentation, pattern recognition, and low visual noise.

## 2. Repository Shape

Create a Rust workspace with one CLI binary:

```text
Cargo.toml
src/
  main.rs
  cli.rs
  config.rs
  contracts.rs
  fixtures.rs
  compiler.rs
  revm_runner.rs
  pipeline.rs
  results.rs
  diff.rs
  report.rs
  bytecode_view.rs
  util.rs
suite/
  purplebench.toml
  contracts/
    0x1111111111111111111111111111111111111111.sol
  fixtures/
    0x1111111111111111111111111111111111111111/
      deposit.json
      withdraw.json
runs/
site/
```

Primary binary:

```text
purplebench
```

Core commands:

```text
purplebench init
purplebench capture --rpc-url <url> --tx <hash> --contract <address>
purplebench validate --suite suite/purplebench.toml
purplebench run --suite suite/purplebench.toml --compiler /path/to/solc --compiler-id <id>
purplebench diff --run runs/<new> --baseline runs/<base>
purplebench report --runs runs --out site
```

Only `capture` is allowed to use RPC. `validate`, `run`, `diff`, and `report`
must operate entirely from local files.

## 3. Suite Configuration

Use `purplebench.toml` for suite-level configuration.

Contracts are stored as flattened Solidity files. The filename is the target
contract address plus `.sol`.

Example:

```text
suite/contracts/0x1111111111111111111111111111111111111111.sol
```

Transactions reference the contract address whose runtime bytecode will be
replaced during simulation.

Example `purplebench.toml`:

```toml
[suite]
name = "mainnet-sampled"
chain_id = 1
evm_spec = "cancun"

[[optimization_profiles]]
id = "default"
optimizer = false
via_ir = false
runs = 0

[[optimization_profiles]]
id = "optimized"
optimizer = true
via_ir = false
runs = 200

[[optimization_profiles]]
id = "optimized-high-runs"
optimizer = true
via_ir = false
runs = 10000

[[optimization_profiles]]
id = "via-ir"
optimizer = true
via_ir = true
runs = 200

[[optimization_profiles]]
id = "via-ir-high-runs"
optimizer = true
via_ir = true
runs = 10000

[[contracts]]
address = "0x1111111111111111111111111111111111111111"
source = "contracts/0x1111111111111111111111111111111111111111.sol"
contract_name = "Vault"

[[transactions]]
id = "deposit"
contract = "0x1111111111111111111111111111111111111111"
fixture = "fixtures/0x1111111111111111111111111111111111111111/deposit.json"

[[transactions]]
id = "withdraw"
contract = "0x1111111111111111111111111111111111111111"
fixture = "fixtures/0x1111111111111111111111111111111111111111/withdraw.json"
```

The `contract_name` is needed because one flattened file can still contain
multiple contracts. The benchmarked runtime bytecode is extracted from that
named contract.

## 4. Contract Input Model

Contract source files are flattened `.sol` files, one per contract address.

Rules:

- The filename must be the lowercase checksummed-or-hex address plus `.sol`.
- The configured `contract_name` identifies which compiled contract output to
  use from the file.
- Imports are not expected during benchmark runs. If imports are present,
  validation fails unless the suite explicitly enables local import resolution.
- Compilation uses Solidity standard JSON generated by the tool from the
  flattened source.
- The source path and address are included in run metadata for traceability.

Generated standard JSON should include:

```json
{
  "language": "Solidity",
  "sources": {
    "0x1111111111111111111111111111111111111111.sol": {
      "content": "<flattened source>"
    }
  },
  "settings": {
    "optimizer": {
      "enabled": true,
      "runs": 200
    },
    "viaIR": false,
    "outputSelection": {
      "*": {
        "*": [
          "evm.deployedBytecode.object",
          "evm.deployedBytecode.opcodes",
          "metadata"
        ]
      }
    }
  }
}
```

Do not remove metadata from `evm.deployedBytecode.object`. Runtime bytecode size
is computed from the exact hex string returned by the compiler.

## 5. Transaction Fixture Model

Each transaction fixture must contain enough information to replay the sampled
transaction locally with revm and no network access.

Example shape:

```json
{
  "id": "deposit",
  "chain_id": 1,
  "evm_spec": "cancun",
  "contract": "0x1111111111111111111111111111111111111111",
  "block": {
    "number": "0x0121c500",
    "timestamp": "0x...",
    "base_fee_per_gas": "0x...",
    "gas_limit": "0x...",
    "coinbase": "0x...",
    "prevrandao": "0x..."
  },
  "tx": {
    "from": "0x...",
    "to": "0x1111111111111111111111111111111111111111",
    "value": "0x0",
    "data": "0x...",
    "gas_limit": "0x...",
    "gas_price": "0x...",
    "max_fee_per_gas": null,
    "max_priority_fee_per_gas": null,
    "access_list": []
  },
  "accounts": {
    "0x...": {
      "nonce": "0x1",
      "balance": "0x...",
      "code": "0x...",
      "storage": {
        "0xslot": "0xvalue"
      }
    }
  },
  "expected": {
    "success": true,
    "revert_data_hash": null,
    "logs_hash": "0x...",
    "storage_after": {
      "0x1111111111111111111111111111111111111111": {
        "0xslot": "0xexpected_final_value"
      }
    }
  }
}
```

Fixture requirements:

- `contract` identifies the address whose code is replaced with newly compiled
  runtime bytecode.
- `accounts` contains the pre-transaction state.
- `expected.storage_after` contains all storage slots whose final values are
  part of the transaction recording.
- Storage validation compares the final value of each recorded slot after the
  simulated transaction.
- Missing storage access during simulation is a fixture error.
- Additional storage writes can be recorded as warnings at first, but the
  default long-term policy should be strict: any touched storage slot not
  included in the recording fails validation.

Gas is recorded as a metric, but it is not used as a correctness assertion.

## 6. Fixture Capture

Implement `purplebench capture` as a separate workflow.

Inputs:

- RPC URL.
- Mainnet transaction hash.
- Contract address to benchmark.
- Optional output path.
- Optional transaction label.

Capture flow:

1. Fetch transaction, receipt, and block metadata.
2. Use debug/prestate tracing to collect all accounts and storage slots needed
   to execute the transaction from its pre-state.
3. Capture code, balance, nonce, and touched storage values.
4. Replay the original transaction locally in revm using only captured state.
5. Compare local replay result to the real receipt status and logs hash.
6. Capture final storage values for all touched slots.
7. Write a canonical fixture JSON with sorted accounts and sorted storage keys.
8. Run validation on the written fixture.

Capture can use network access. Benchmark runs cannot.

If the RPC provider cannot return sufficient prestate data, fail with a clear
message explaining which state was missing.

## 7. Offline State Database

Implement a fixture-backed revm database.

Behavior:

- Account lookup returns only accounts present in the fixture.
- Code lookup returns only code present in the fixture or the substituted
  compiled runtime bytecode for the target contract address.
- Storage lookup returns only slots present in the fixture.
- Missing account, code, or storage access fails the simulation with
  `MissingState`.

This intentionally prevents accidental remote fetching or silently treating
missing state as zero.

Each simulation gets an isolated DB instance so parallel runs cannot share
mutable state.

## 8. Compiler Pipeline

For each `(contract, optimization_profile)` pair:

1. Read the flattened Solidity file.
2. Generate standard JSON input.
3. Apply the optimization profile.
4. Run the selected `solc` binary with `--standard-json`.
5. Parse compiler output.
6. Extract `evm.deployedBytecode.object` for the configured `contract_name`.
7. Compute runtime bytecode size from the exact returned bytecode.
8. Compute runtime bytecode hash.
9. Write runtime bytecode to disk immediately.
10. Send the compiled artifact to the simulation queue.

The compiler stage must be parallelized with a bounded worker pool.

Compiler artifacts:

```text
runs/<run-id>/artifacts/
  0x1111111111111111111111111111111111111111/
    default/
      runtime.hex
      compiler-stderr.txt
      compiler-meta.json
    optimized/
      runtime.hex
      compiler-stderr.txt
      compiler-meta.json
```

Avoid storing full compiler-generated JSON as the long-term contract input
format. The source of truth is the flattened `.sol` file plus the suite config.
Small `compiler-meta.json` files are acceptable as run artifacts if they contain
only benchmark metadata, selected warnings, hashes, sizes, and timing.

## 9. Simulation Pipeline

For each compiled artifact and each transaction referencing that contract:

1. Load the transaction fixture.
2. Build a revm environment from the fixture block and transaction.
3. Load pre-transaction accounts and storage into the fixture DB.
4. Substitute the compiled runtime bytecode at the fixture `contract` address.
5. Execute the transaction.
6. Record gas used.
7. Record success/revert status.
8. Record logs hash and revert data hash if applicable.
9. Compare post-transaction storage against `expected.storage_after`.
10. Record storage mismatches as correctness failures.

Correctness checks:

- Transaction success/revert status should match the recording.
- Revert data hash should match when the recording includes one.
- Logs hash should match when the recording includes one.
- Final storage values for recorded slots must match.
- Missing state is a fixture failure.

Gas is not a correctness check. It is the benchmark metric.

## 10. Parallel Execution

Use a streaming pipeline:

```text
compile workers
  -> write runtime bytecode artifact
  -> send compiled artifact to simulation queue

simulation workers
  -> run all matching transaction fixtures
  -> send result to result writer

result writer
  -> append journal entries
  -> produce final sorted CSV files
```

Implementation details:

- Use `rayon` or `tokio` plus blocking worker pools. Prefer the simpler model
  unless async is needed for process management.
- Bound compiler parallelism separately from simulation parallelism.
- Start simulations as soon as a compile artifact is available.
- Keep final CSV deterministic by sorting rows before final write.
- Write a journal during the run so partial failures can be inspected.
- Never mutate shared fixture state across simulations.

## 11. Run Output

Suggested run layout:

```text
runs/
  solc-commit-abc123/
    meta.json
    artifacts/
    csv/
      compilations.csv
      transactions.csv
      storage_checks.csv
      summary.csv
      failures.csv
    diff.txt
```

`compilations.csv`:

```text
run_id,compiler_id,contract,contract_name,profile,success,runtime_size_bytes,runtime_hash,bytecode_path,compile_ms,error
```

`transactions.csv`:

```text
run_id,compiler_id,contract,profile,tx_id,success,gas_used,baseline_gas_used,gas_delta,gas_pct,status_match,logs_match,revert_data_match,storage_match,duration_ms,error
```

`storage_checks.csv`:

```text
run_id,compiler_id,contract,profile,tx_id,account,slot,expected,actual,match
```

`summary.csv`:

```text
run_id,compiler_id,profile,total_runtime_size,total_gas,mean_gas,median_gas,tx_count,compile_failures,sim_failures,storage_failures
```

`failures.csv`:

```text
run_id,compiler_id,stage,contract,profile,tx_id,error_kind,error
```

## 12. Baseline Diffing

Support:

```text
purplebench run --baseline runs/<baseline>
purplebench diff --run runs/<new> --baseline runs/<baseline>
```

Diff matching keys:

- Compilation rows: `contract + profile`.
- Transaction rows: `contract + profile + tx_id`.
- Storage rows: `contract + profile + tx_id + account + slot`.

Diff behavior:

- Report runtime bytecode size deltas and percentage changes.
- Report gas deltas and percentage changes.
- Report correctness failures separately from gas movement.
- Report missing rows, new rows, compile failures, simulation failures, and
  storage mismatches.
- A gas increase or decrease is not a failure by itself.
- A storage mismatch is a correctness failure.

Text output example:

```text
CORRECTNESS FAILURES
storage mismatch vault optimized deposit 0x... slot 0x...
  expected 0x01
  actual   0x00

GAS REGRESSIONS
+12.4%  0x1111... optimized deposit     100000 -> 112400
+8.1%   0x1111... default   withdraw    200000 -> 216200

GAS IMPROVEMENTS
-5.3%   0x1111... via-ir    liquidate   300000 -> 284100

RUNTIME BYTECODE SIZE
+96 B   0x1111... optimized             12400 -> 12496
-12 B   0x1111... via-ir-high-runs      12380 -> 12368
```

## 13. HTML Reports

Generate static HTML from CSV files. No backend and no remote assets.

Output:

```text
site/
  index.html
  compilers/
    solc-commit-abc123.html
  bytecode/
    solc-commit-abc123/
      0x1111111111111111111111111111111111111111/
        optimized.html
  assets/
    style.css
```

Top-level page:

- Scatter plot of aggregate runtime bytecode size vs aggregate gas.
- One compiler run per point, with profile breakdown available in table form.
- Table for each compiler version below the graph.
- Links to compiler pages.

Compiler page:

- Gas/runtime-size scatter plot per transaction/profile vs baseline.
- Compilation table:
  - contract address
  - contract name
  - optimization profile
  - runtime bytecode size
  - size delta
  - percentage delta
  - bytecode hash
  - bytecode page link
- Transaction table:
  - transaction id
  - contract
  - profile
  - gas used
  - gas delta
  - gas percentage
  - status/log/revert/storage checks
- Storage mismatch table when present.

Bytecode page:

- Render raw runtime bytecode.
- Each byte cell is colored by byte value from `0..255`.
- Decode opcodes enough to identify `PUSH1` through `PUSH32`.
- Push opcodes and their immediate bytes use a different hue.
- Cell tooltip includes byte offset, byte value, opcode role, and push group.
- Keep the display dense. Avoid broad spacing and decorative panels.

Use a Solidity-inspired palette:

```css

```

Style rules:

- Dense tables.
- Sticky table headers.
- Right-aligned numeric columns.
- Monospace for bytecode, hashes, addresses, slots, and numeric benchmark
  values.
- Red for gas increases and correctness failures.
- Green for gas decreases.
- Purple/blue for neutral compiler and bytecode information.
- No large dashboard padding.
- No decorative floating metrics inside table cells.
- No external fonts, scripts, or CDNs.

## 15. Validation

`purplebench validate` should check:

- Every configured contract source exists.
- Contract source filename matches configured address.
- Every transaction references a configured contract.
- Every fixture exists.
- Fixture contract matches transaction contract.
- Fixture can be loaded and parsed.
- Fixture has block, tx, account, code, and storage data.
- Fixture has expected post-transaction storage values.
- The original fixture transaction replays successfully against original code.
- The replayed storage values match the recorded expected storage values.
- No network access is required for validation.

Validation should fail loudly before benchmark work begins.

## 16. Testing Strategy

Unit tests:

- TOML config parsing.
- Address filename validation.
- Flattened source to standard JSON generation.
- Optimization profile application.
- Compiler output parsing.
- Runtime bytecode size calculation including metadata.
- Runtime bytecode hash calculation.
- Bytecode opcode and PUSH decoding.
- CSV serialization order.
- Gas delta and percentage formatting.
- Storage comparison logic.
- Missing-state DB behavior.

Integration tests:

- Tiny Solidity contract compiled with local `solc` if available.
- Hand-authored fixture that executes in revm.
- Original-code replay validates storage recording.
- Code substitution preserves account storage and changes only code.
- Parallel run produces deterministic CSV.
- Diff output separates gas changes from correctness failures.
- Static HTML report generation from sample CSV.
- Bytecode page renders expected PUSH coloring metadata.

Performance tests:

- Compile and simulation stages overlap.
- Simulation workers run in parallel.
- Large fixture loading does not dominate runtime.
- Benchmark `run` performs no RPC or network calls.

## 18. Early Technical Decisions

Runtime bytecode size:

- Use only `evm.deployedBytecode.object`.
- Include metadata.
- Compute bytes as decoded hex length.

Gas:

- Record and compare gas.
- Do not fail correctness solely due to gas movement.

Storage:

- Compare post-transaction storage against the recording.
- Treat mismatches as correctness failures.
- Treat missing state as fixture failures.

Contract input:

- Store flattened Solidity source files.
- Filename is contract address plus `.sol`.
- Do not store compiler-generated JSON as the source input format.

Reports:

- CSV is the canonical output.
- HTML is generated from CSV.
- Text diff is generated for development-loop and agent use.
